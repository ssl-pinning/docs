Формат подписанного реестра ​

Тело ответа GET /api/v1/{file} — единый JSON-объект с двумя полями верхнего уровня.

json
{
  "payload": {
    "keys": [
      {
        "date": "2026-03-24T23:39:22.964574+01:00",
        "domainName": "www.google.com",
        "expire": 4736419,
        "fqdn": "google.com",
        "key": "b8tZqtqfv0RVKfwivfzaXuFWFHkYP4ufBhb5esciCwo="
      },
      {
        "date": "2026-03-24T23:39:22.963066+01:00",
        "domainName": "mail.google.com",
        "expire": 4736550,
        "fqdn": "mail.google.com",
        "key": "1o0e39oKjV5hGki9WnKOeg2Hs1qQSRjMgWpbL3ajP4U="
      }
    ]
  },
  "signature": "Zl8cwtiAoEjvdmFXReiioVk3zUM2ymbQGa2hIxvixNR3..."
}

Поля верхнего уровня ​

ПолеТипОписание
payloadобъектСодержит keys — массив записей пинов. См. Проверку подписи, прежде чем доверять любому значению внутри.
signatureстрока, Base64RSA PKCS#1 v1.5 подпись, вычисленная над SHA-512 хэшем JCS-канонизированного payload, приватным RSA-4096 ключом сервера.

Поля записи payload.keys[] ​

ПолеТипОписание
domainNameстрокаПаттерн хостнейма, к которому применяется пин на клиенте (например, host-паттерн CertificatePinner на Android). Может отличаться от fqdn, если балансировщик обслуживает несколько хостнеймов с разными сертификатами.
keyстрока, Base64SHA-256 хэш Subject Public Key Info (SPKI) сертификата — значение, по которому пиннится, с префиксом sha256/ там, где клиентский API ожидает такой формат.
expireцелое числоКоличество секунд до истечения отслеживаемого сертификата на момент захвата пина. Не cache-control значение — сервер непрерывно обновляет пины независимо от этого числа.
dateстрока, ISO 8601 со смещениемТаймстамп последнего обновления именно этого пина на сервере.
fqdnстрокаДомен, к которому сервер подключался по TLS, чтобы получить сертификат, из которого выведен этот пин.

Проверка подписи ​

  1. Взять сырой JSON-текст payload ровно в том виде, в котором он присутствует в HTTP-ответе — до десериализации в какую-либо нативную для языка структуру.
  2. Канонизировать этот текст по JCS (RFC 8785): ключи объекта отсортированы по Unicode code point, без незначащих пробелов, стандартная сериализация чисел и строк.
  3. Вычислить SHA-512 канонизированных UTF-8 байт.
  4. Base64-декодировать signature.
  5. Проверить её против этого хэша алгоритмом RSA PKCS#1 v1.5, используя публичный ключ, встроенный в клиент.
  6. Только при успехе разобрать payload.keys и использовать его содержимое. При неудаче — отбросить весь ответ целиком: частично доверенный реестр не поддерживаемое состояние.

Почему выбрана именно эта схема (JCS + SHA-512 + RSA PKCS#1 v1.5) — см. Архитектуру, а разбор с нуля, если вы не используете один из официальных SDK — в разделе Реализация собственного коннектора.
