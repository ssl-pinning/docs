Архитектура ​

Обычный HTTPS доверяет любому сертификату, который подписал доверенный CA. А доверенных CA в системе — сотни. Любой из них может по ошибке или по принуждению выпустить сертификат для чужого домена — и клиент примет его как настоящий.

SSL-пиннинг закрывает эту дыру. Вместо «любой сертификат от любого доверенного CA» приложение проверяет конкретный, заранее известный публичный ключ защищаемого домена. Любое соединение с другим ключом отклоняется — это закрывает все векторы атак из раздела Модель угроз.

Сам реестр подписан, поэтому список ключей нельзя подделать при передаче. А поскольку ssl-pinning сервер обновляет реестр в реальном времени, ротация сертификата больше не требует нового релиза приложения — именно это было главной операционной проблемой статического пиннинга.

Компоненты ​

Сервис состоит из двух частей: сервера, который мониторит сертификаты и отдаёт подписанный реестр, и клиента, который проверяет и применяет этот реестр.

┌───────────────────┐    GET /api/v1/keys.json      ┌──────────────────────┐
│   Client app      │ ────────────────────────────→ │  ssl-pinning server  │
│                   │ ←──────────────────────────── │                      │
│ RSA signature     │  { payload: { keys: [...] },  │  Worker → TLS :443   │
│ verification      │    signature: "..." }         │  SHA-256(pubkey)     │
│                   │                               │  RSA-signs registry  │
│ OkHttp            │                               └──────────────────────┘
│ CertificatePinner │                                           ↑
└───────────────────┘                                Updated every 5 seconds

Для каждого настроенного домена сервер запускает отдельный монитор. Монитор следит за TLS-сертификатом домена и его публичным ключом.

Раз в заданный интервал монитор сбрасывает дамп собранных пинов в хранилище, откуда HTTP-хендлер отдает их с собранной подписью.

Криптографическая цепочка ​

Перед подписью сервер канонизирует JSON payload по спецификации JCS, RFC 8785 — это гарантирует, что порядок ключей, пробелы и кодировка не влияют на подпись. Вычисляется SHA-512 хэш канонизированного текста и подписывается RSA PKCS#1 v1.5 приватным ключом сервера, который никогда не покидает сервер.

Клиент выполняет ту же цепочку в обратном порядке:

  1. Получить необработанную JSON-строку поля payload из ответа — до десериализации. Так сохраняется точное байтовое представление, которое было подписано: любое переформатирование (другой порядок ключей, лишние пробелы) изменит байты и сделает подпись невалидной.
  2. Канонизировать эту строку по JCS (RFC 8785): отсортировать ключи по Unicode code point, убрать незначащие пробелы.
  3. Вычислить SHA-512 хэш канонизированной строки.
  4. Декодировать поле signature из Base64.
  5. Проверить подпись по RSA-публичному ключу, встроенному в клиент (APK / IPA).
  6. Если проверка прошла — десериализовать payload.keys и применить их в пиннинг-клиенте. Если не прошла — прервать инициализацию: запиненный клиент не создаётся, и ни один сетевой запрос через него не уходит.

Даже если реестр подделан на уровне сети, без приватного ключа невозможно получить валидную подпись — клиент обнаружит подделку раньше, чем станет доверять какому-либо пину.

Формат подписанного реестра ​

Ответ сервера содержит два поля верхнего уровня: payload (текущие пины) и signature (RSA-подпись, которую клиент должен проверить перед использованием данных).

json
{
  "payload": {
    "keys": [
      {
        "date": "2026-03-24T23:39:22.964574+01:00",
        "domainName": "www.google.com",
        "expire": 4736419,
        "fqdn": "google.com",
        "key": "b8tZqtqfv0RVKfwivfzaXuFWFHkYP4ufBhb5esciCwo="
      }
    ]
  },
  "signature": "Zl8cwtiAoEjvdmFXReiioVk3zUM2ymbQGa2hIxvixNR3..."
}
ПолеОписание
domainNameПаттерн хоста, к которому применяется пин на клиенте
keyBase64-кодированный SHA-256 хэш публичного ключа сертификата (SPKI)
expireКоличество секунд до истечения сертификата на момент захвата пина
dateТаймстамп последнего обновления пина на ssl-pinning сервере
fqdnДомен, к которому сервер подключался по TLS, чтобы получить сертификат
signatureRSA PKCS#1 v1.5 + SHA-512 подпись над JCS-канонизированным payload

Несколько доменов можно сгруппировать в один файл ответа через опцию конфига keys[].file — полезно, когда несколько хостнеймов используют общий балансировщик и общий сертификат, или когда просто хочется меньше round trip'ов на клиенте.

Бэкенды хранения ​

Сервер мониторит ключи в памяти и периодически делает снэпшот в одно из четырёх хранилищ:

ТипСценарий использования
memoryРазработка и тесты; данные не переживают рестарт
fsЗаписывает JSON-файлы на диск и отдаёт их напрямую
redisНесколько инстансов сервера делят общее хранилище
postgresПерсистентное хранилище с историей

Полный список опций — в разделе Конфигурация сервера.

Шифрование данных на диске и TLS до самого хранилища — ответственность оператора: сервер ничего не шифрует поверх того, что настроено в storage.dsn (sslmode для PostgreSQL, TLS-опции для Redis) и на уровне самого хранилища или диска.

Генерация ключей подписи ​

Перед первым запуском сгенерируйте пару ключей RSA-4096:

bash
$ git clone git@github.com:ssl-pinning/ssl-pinning.git && cd ssl-pinning
$ task generate-keys
# → build/package/etc/ssl-pinning/tls/prv.pem  (приватный ключ, остаётся на сервере)
# → build/package/etc/ssl-pinning/tls/pub.pem  (публичный ключ, встраивается в клиент)

Приватный ключ подписывает реестр и никогда не должен передаваться клиенту. Публичный ключ — единственный криптографический артефакт, встроенный в приложение; его срок жизни полностью отделён от ротации TLS-сертификатов — именно это делает всё остальное операционно устойчивым при сокращающемся сроке жизни сертификатов (см. Зачем нужен динамический пиннинг).

Хранение, ротация и уничтожение prv.pem после его создания — зона ответственности оператора, не ssl-pinning. Сервер только читает ключ из tls.dir при старте; как именно он туда попадает — решает оператор: Kubernetes Secret, смонтированный в под (см. пример в Self-hosting), bind-mount с хоста, или интеграция с внешним секрет-менеджером (Vault, AWS/GCP Secrets Manager). Ни task generate-keys, ни сам сервер не управляют жизненным циклом ключа дальше его генерации.
