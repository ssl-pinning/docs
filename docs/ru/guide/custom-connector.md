# Реализация собственного коннектора

Использование [Android](./android-sdk) или [iOS/macOS](./ios-macos-sdk) SDK необязательно. Протокол, который они реализуют, публичный и описан здесь — клиент может получить реестр, проверить его и применить пины любым HTTP/TLS-стеком, который уже используется. Это та же спецификация, которой следуют оба официальных SDK; полное криптографическое обоснование — в разделе [Архитектура](./architecture).

## Что должен делать ваш коннектор

1. **Получить** реестр по HTTPS: `GET` на настроенный эндпоинт, распарсить JSON-объект верхнего уровня — `payload` и `signature`. Захватить сырую JSON-подстроку `payload` ровно в том виде, в котором она получена, **до** какой-либо десериализации. Именно эта побайтовая строка покрывается подписью; её переcериализация (другой порядок ключей, другие пробелы) сделает проверку невалидной.
2. **Канонизировать** эту сырую строку по спецификации [JCS, RFC 8785](https://datatracker.ietf.org/doc/html/rfc8785): отсортировать ключи объекта по Unicode code point, убрать незначащие пробелы, применить стандартные правила сериализации чисел и строк.
3. **Хэшировать** канонизированные байты алгоритмом SHA-512.
4. **Проверить** поле `signature` (после Base64-декодирования) против этого хэша алгоритмом RSA PKCS#1 v1.5, используя публичный ключ, встроенный в ваше приложение (`pub.pem`, сгенерированный вместе с ключом подписи на сервере — см. [Генерация ключей подписи](./architecture#генерация-ключеи-подписи)). Принимайте публичный ключ в удобном для вашей стратегии встраивания формате: PEM, Base64-кодированный PEM, или сырой DER (SPKI) — оба официальных SDK поддерживают все три формата именно по этой причине.
5. **Fail closed.** Если подпись не проверяется, эндпоинт недоступен, или ответ некорректно сформирован — не создавайте запиненный клиент и не откатывайтесь молча на незапиненный. Прервите инициализацию или перейдите в деградированный, видимый пользователю режим. Ни один официальный SDK никогда не создаёт частично проверенный или "best-effort" запиненный клиент — здесь нет безопасной середины.
6. **Применить пины.** После успешной проверки десериализуйте `payload.keys` и настройте пиннинг сертификата/публичного ключа вашего HTTP-клиента SHA-256 SPKI-хэшем из поля `key` каждой записи, привязанным к её `domainName`. Точное значение полей — в разделе [Формат подписанного реестра](./architecture#формат-подписанного-реестра).

```
ваше приложение
   │
   ├─ GET <endpoint>                         → { payload, signature }
   ├─ canonicalize(raw payload string)  [JCS]
   ├─ sha512(canonical)
   ├─ verify(signature, hash, embedded pubkey)  [RSA PKCS#1 v1.5]
   │    ├─ fail  → прервать / деградированный режим, без запиненного клиента
   │    └─ pass  → разобрать payload.keys
   │                для каждого ключа: запинить sha256(SPKI) к domainName
   │                в механизме пиннинга вашего TLS/HTTP-стека
   └─ готово
```

## Почему это безопасно делать самостоятельно

Подпись реестра — единственное, что стоит между подделанным и доверенным ответом, и это стандартная RSA-подпись над стандартной схемой канонизации, а не проприетарный протокол. Любая платформа с примитивом проверки RSA-подписи и корректной реализацией JCS может валидировать её правильно. Два официальных SDK существуют ради удобства (настройка HTTP-клиента, интеграция с API пиннинга) — а не потому, что сам протокол требует специфичного для платформы доверия.
